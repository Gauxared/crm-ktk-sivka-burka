# Хранение данных MVP «Сивка-Бурка»

Status: ACCEPTED
Задача: ARCH-006. Версия: 1.0. Дата: 2026-09-13.
Основание: [требования](requirements.md), [архитектура](architecture.md),
[домен](domain-model.md), [переходы](booking-flow.md), [API](api.md).
Это принятая спецификация схемы и транзакций. Миграции, работающая БД и интеграционные
тесты в этой задаче не создаются. Названия таблиц нормативные; SQL оформляется отдельной задачей.

## 1. Выбор и границы

PostgreSQL, как предусмотрено ARCH-002; одна база одного клуба. Конкретная поддерживаемая
версия сервера, драйвер и средство миграций фиксируются при подготовке окружения.
Нет tenant_id с обещанием готовой многопользовательской платформы, таблиц лошадей,
вместимости, банковских транзакций или автоматического допуска к услуге.

Запросы лендинга, обоих ботов и владельца используют один прикладной слой и одну схему.
Runtime-роль БД не является владельцем схемы; миграции выполняет отдельная роль.
Прямое изменение бизнес-таблиц сторонними скриптами не входит в поддерживаемый протокол.

Для коротких бизнес-записей MVP выбирается READ COMMITTED и единая строка
business_write_guard(id=1), захватываемая SELECT ... FOR UPDATE первым действием
транзакции. Её используют все изменения каталога, контактов, заявок, прогулок,
участий, денег, черновиков, входящих событий, ключей операций и очистка этих данных.
Так одновременно выполняется одна бизнес-транзакция, независимо от числа процессов backend.
Это техническая сериализация записи, не ограничение числа клиентов или прогулок.
Строка guard создаётся миграцией; runtime не вправе удалять её. Отсутствие строки —
ошибка конфигурации с отказом записи, а не разрешение работать без блокировки.

Сессии и доставка уже созданных notification_jobs используют собственные транзакции.
Сетевые вызовы, ожидание ответа человека и генерация текста не выполняются под guard.
Начальные конфигурируемые пределы: lock_timeout 2 s, statement_timeout 5 s;
ожидание/ошибка блокировки приводит к rollback и повтору прежнего ключа, не частичному успеху.
Перед масштабированием возможна отдельная замена guard на блокировки агрегатов с тестами гонок.
Сейчас более сложный порядок блокировок не требуется.

Механика блокировки строки до конца транзакции описана в
[PostgreSQL Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html).
Это обоснование механизма, а не результат проверки ещё не реализованной системы.

## 2. Типы и общие ограничения

- PK бизнес-объектов — uuid, наружу сериализуется непрозрачной строкой. Внешние ID платформ
  — text: sender и conversation не приводятся к одному числу.
- created_at/recorded_at — timestamptz от сервера; фактическое occurred_at вводит владелец.
  start_at — timestamptz. requested_date — date, requested_time_text — text; отдельно
  requested_timezone — снимок IANA-зоны клуба. NULL не превращается в полночь.
- Версии — bigint NOT NULL CHECK(version > 0), изменяются сервером.
- Суммы — bigint копеек, currency text CHECK(currency='RUB'). Для заданной цены и ожидания
  0..9000000000000, для фактической отметки 1..9000000000000. Неизвестная сумма — NULL.
  Бесплатный сценарий не добавляется: сохраняется граница ARCH-003/005.
- Суммирование — numeric, без переполнения bigint и двоичной плавающей точки. Сводные суммы,
  выходящие за точное представление API Money, дают явную диагностируемую ошибку, не округление;
  отдельная отметка не теряется. Тест граничных сумм обязателен в реализации.
- participants_count integer CHECK > 0, duration_minutes integer NULL либо > 0.
  Верхняя граница integer техническая; это не бизнес-вместимость.
- Перечисления — text с CHECK по утверждённым значениям. У статусов нет независимого is_paid.
- Строковые пределы API проверяются сервером и CHECK для обычных колонок; JSONB проверяется
  по версии DTO перед записью. JSONB применяется к снимкам/ограниченным payload, не вместо FK.
- FK по умолчанию ON DELETE RESTRICT. Каскадное удаление истории вместе с заявкой запрещено.
  Индексы на ссылающихся колонках создаются явно. Секреты ботов не хранятся в этих таблицах.
- Поля таблиц обязательны, если явно не указано NULL; необязательный текст допускает пустую
  строку, необязательная атрибуция — {}. requested_date/time_text допускают NULL для ручной
  заявки без пожелания. Для канальной заявки contact_value может быть доверенным sender ID;
  conversation_id сохраняется отдельно в исходном канальном снимке, не подменяет человека.

## 3. Каталог, настройки и контакты

| Таблица | Основные поля и ограничения |
| --- | --- |
| club_settings | id=1 PK, timezone, catalog_version, contact_info/location_link/visit_rules, version; зона валидируется приложением |
| services | id PK, code UNIQUE, title, description, information, active, sort_order |
| service_options | id PK, service_id FK, code UNIQUE, duration_minutes NULL, pricing_mode, price_minor NULL, currency, active |
| contact_cards | id PK, version, created_at; техническая карточка без клиентского аккаунта |
| channel_identities | id PK, contact_id FK, platform TELEGRAM/VK, integration_id, external_sender_id; UNIQUE(platform,integration_id,external_sender_id) |

FIXED_PER_PERSON требует заданной цены; NEGOTIATED требует price_minor IS NULL.
Согласованная индивидуальная цена хранится в заявке и может отличаться от каталога.
Смена каталога атомарно увеличивает catalog_version; скрытие не удаляет строки.
Снимки заявки сохраняют названия, длительность, модель/цену и версию прочитанного каталога.
Публикация каталога читает настройки и варианты в одном согласованном снимке.

Для формы и ручного ввода создаётся отдельный contact_card; телефон/имя не UNIQUE.
Проверенная идентичность того же бота может повторно использовать карточку контакта.
Интеграция имеет стабильный локальный ID; ротация токена бота не создаёт новую область ID.
Межканального слияния и команды объединить контакты в MVP нет.

Имя и способ связи хранятся в inquiry как исходный неизменяемый contact_snapshot и текущие
requester_name/contact_kind/contact_value. UPDATE_DETAILS меняет данные только этой заявки.
API current_contact означает текущие данные связи по этой заявке, а не глобальное
переписывание всех обращений contact_card. Identity из доверенного адаптера неизменяема
через UPDATE_DETAILS. Ошибочная связь исправляется отдельной административной процедурой
с историей до появления специального интерфейса; автослияние не используется.

## 4. Заявка, план и участия

| Таблица | Основные поля |
| --- | --- |
| inquiries | id PK, contact_id FK, channel_identity_id FK NULL, source_kind, received_at, status, version; исходные contact_snapshot/selection_snapshot JSONB; текущие requester_name/contact_kind/contact_value; requested_date/time_text/timezone; experience; comment, owner_note; acquisition JSONB |
| inquiry_terms | inquiry_id PK/FK, service_option_id FK, participants_count, duration_minutes NULL, total_minor NULL, expected_prepayment_minor NULL, currency, note |
| visits | id PK, service_id FK, status, version, start_at, duration_minutes NULL, created_at |
| visit_participations | id PK, inquiry_id FK, visit_id FK, joined_at, closed_at NULL, close_kind NULL, participants_snapshot NULL, plan_snapshot NULL, completion_voided_at NULL, completion_void_reason NULL |

Inquiry.status: NEW/NEGOTIATING/CONFIRMED/COMPLETED/CANCELLED.
Visit.status: PLANNED/COMPLETED/CANCELLED. inquiry_terms существует ровно одна на заявку;
при создании вариант/количество из выбора, длительность из варианта либо NULL, итог и
ожидаемая предоплата NULL. Прайс × количество — ориентир UI, не автоматически согласованная цена.
Версия inquiry_terms отдельно не вводится: она часть версии Inquiry.
Начальное количество/пожелания входят в исходный снимок; текущие количества берутся из terms,
чтобы InquirySummary и AgreedTerms не содержали конкурирующих изменяемых значений.

Активность участия = closed_at IS NULL. Частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX one_active_participation_per_inquiry
ON visit_participations (inquiry_id) WHERE closed_at IS NULL;
```

Это иллюстрация обязательного ограничения, не миграция для запуска.
close_kind: MOVED/UNSCHEDULED/CANCELLED/PROVIDED. CHECK связывает NULL closed_at и close_kind;
closed_at >= joined_at. Для закрытой связи сохраняются количество и снимок плана на закрытие.
Для PROVIDED дополнительно сохраняются фактические условия заявки в plan_snapshot.
Исторические участия не исчезают после переноса и не пересчитываются от текущей цены/плана.
Ошибочный PROVIDED не удаляется: CORRECT_COMPLETION помечает его отменённым фактом с причиной
и событием истории; закрытая связь остаётся закрытой. Затем при необходимости создаётся новая.
Текущий факт оказания = PROVIDED и completion_voided_at IS NULL. CHECK разрешает void только
для PROVIDED и требует причину; предыдущий факт остаётся доступен в истории.

Межтабличные инварианты проверяет прикладная транзакция под guard:

1. CONFIRMED имеет ровно одно активное участие в PLANNED; COMPLETED/CANCELLED не имеют активных.
2. Активное участие допустимо для NEGOTIATING/CONFIRMED; назначение NEW сначала переводит в NEGOTIATING.
3. Формат и известная длительность совместимы с общей прогулкой по ARCH-005; NULL не подменяется числом.
4. Завершение Visit требует хотя бы одного неотменённого факта PROVIDED по всей истории и отсутствия активных участий.
5. Отмена Visit требует отсутствия таких фактов и активных участий. Пустой PLANNED остаётся видимым.
6. Исправление факта в закрытом Visit требует сначала REOPEN_VISIT: нельзя оставить COMPLETED без
   единственного оказания. API-команда с невыполненным условием получает INVALID_TRANSITION.
7. Изменение контактных данных, условий, статуса или денег активного участника увеличивает
   также version Visit, поскольку они входят в групповой снимок. Команда требует ожидаемые версии.

CHECK не объявляется средством проверки другой таблицы. Реализация обязана покрыть эти
инварианты интеграционными тестами и пропускать все бизнес-записи через общий сервис команд.
Изменение нескольких полей одной командой увеличивает версию каждого затронутого объекта
один раз; CONFIRM_AND_COMPLETE даёт две записи истории в рамках одного commit.

## 5. Ручные суммы и история

cash_notes: id PK, inquiry_id FK, kind RECEIPT/REFUND_NOTE, amount_minor, currency,
occurred_at, recorded_at, owner_id FK, note. Оригинальная строка неизменяема.
cash_note_corrections: id PK, inquiry_id FK, original_note_id UNIQUE,
replacement_note_id UNIQUE NULL, reason, recorded_at, owner_id FK.
Составные FK (inquiry_id,note_id) ссылаются на UNIQUE(inquiry_id,id) cash_notes:
нельзя исправить запись другой заявки или подставить чужую замену.
original_note_id <> replacement_note_id, если замена есть.

Исправление атомарно добавляет correction и при необходимости новую cash_note.
Заменять можно только действующую запись, новая replacement создаётся этой же операцией;
так невозможен цикл исправлений. Повтор с прежним ключом возвращает прежний результат.
Повтор новым ключом для уже исправленного оригинала — CASH_NOTE_SUPERSEDED.
Действующая отметка — та, на которую нет correction.original_note_id.
Замена может быть позже исправлена тем же способом; NULL replacement исключает ошибочную
запись из расчёта, сохраняя причину. Фактический возврат — REFUND_NOTE, а не correction.

CashSummary вычисляется из действующих записей: received, returned, net=received-returned,
balance=total-net либо NULL. Отрицательный balance и возврат сверх поступлений видимы.
Суммы не хранятся дублирующими счётчиками в Inquiry/Visit. У отменённой заявки balance
не объявляется долгом; завершение/подтверждение не имеют проверки достаточности денег.

change_events: id PK, command_id FK, ordinal, recorded_at, actor_kind OWNER/CHANNEL/SYSTEM,
owner_id FK NULL, action, reason NULL, schema_version, changes JSONB.
UNIQUE(command_id,ordinal). event_inquiries(event_id,inquiry_id) и event_visits(event_id,visit_id)
имеют составные PK и FK; одно групповое событие доступно из истории каждого затронутого объекта.
changes содержит ограниченный снимок до/после изменённых полей, без паролей/токенов/сырой переписки.
Это аудит рядом с текущими таблицами, не event sourcing. Контакт в истории — персональные данные,
его очистка должна учитывать и эти JSONB. Обычные команды не удаляют и не переписывают события.

## 6. Идентичность отправки и повтор команды

| Таблица | Ключи и назначение |
| --- | --- |
| operation_receipts | id PK (=command_id), scope_kind, scope_id, method, canonical_path, key_digest, payload_digest, digest_key_version, normalization_version, accepted_at, result_json NULL, result_expires_at NULL, tombstoned_at NULL; UNIQUE(scope_kind,scope_id,method,canonical_path,key_digest) |
| submission_tokens | token_digest PK, issued_at, expires_at, used_receipt_id FK NULL, consumed_at NULL; один токен → не более одной принятой операции |
| receipt_inquiries | receipt_id FK, inquiry_id FK, составной PK; связывает операцию и затронутые заявки для очистки её результата |
| channel_events | id PK, platform, integration_id, event_key_digest, dialog_key_digest, received_at, outcome_kind, receipt_id FK NULL; UNIQUE(platform,integration_id,event_key_digest) |
| conversation_drafts | id PK, channel_identity_id FK, conversation_id, version, answers JSONB, step, expires_at, closed_at NULL; частичный UNIQUE(channel_identity_id,conversation_id) WHERE closed_at IS NULL |

Административный scope включает owner_id; публичный — фиксированный PUBLIC_FORM с путём
подачи; канальный — platform+integration_id. Дедупликация не основана на телефоне или имени.
Ключи и семантический payload хранятся как HMAC с серверным секретом вне БД; версия ключа
позволяет сохранять проверку старых операций при ротации. Обычный SHA хеш телефона не
считается обезличиванием. Исторические ключи HMAC доступны только серверу, не логам.
При поиске повтора сервер вычисляет digest по всем ещё используемым версиям HMAC-ключа
под guard, до вставки с текущей версией. Ротация не должна обходить прежний UNIQUE новым
digest. То же правило и сохранённая digest_key_version нужны токенам и channel_events.
Токен и Idempotency-Key разные: нельзя создать вторую заявку сменой одного из них.

Нормализация payload имеет версию, сохраняемую в receipt: порядок JSON-ключей несущественен,
значимые значения/ожидаемые версии сохраняются; токен/ключ/CSRF/транспортные метаданные
исключены из семантического тела. Игнорируемые рекламные метки исключены. Для старого
receipt применяется его нормализация, а не новая схема развёрнутой версии.

Нет длительно сохранённого RUNNING у синхронной команды: receipt с результатом, изменения,
история и задания уведомления фиксируются одним commit. Конкурентный запрос ожидает guard
или получает временную ошибку; после ожидания читает принятый receipt. До commit сбой
откатывает и receipt, и данные. После commit потерянный HTTP-ответ восстанавливается повтором.
Принятый повтор проверяется до актуальных бизнес-версий/доступности варианта услуги.
Права/CSRF проверяются всегда, до раскрытия результата.

Для формы сначала проверяются известный ключ и использованный токен. Другой ключ с тем
же использованным токеном и тем же payload получает прежнюю безопасную квитанцию;
при другом payload — 409. Новый токен с прежним успешным ключом также не создаёт заявку.
Неиспользованный просроченный токен — 410. После удаления результата остаётся tombstone,
дающий 410 вместо повторного выполнения; публичная квитанция не отражает текущий статус CRM.

Событие бота записывается вместе с изменением черновика либо финальной заявкой и receipt.
Подтверждение приёма внешнему каналу не предшествует надёжному сохранению (конкретный
протокол уточняется адаптером). Повтор старого event не двигает новый шаг черновика.
Новый диалог того же человека может создать новое обращение; ResetDraft закрывает черновик,
не удаляя принятый receipt. Необработанное событие не помечается обработанным до commit.

## 7. Транзакции и согласованные чтения

Общий порядок нового бизнес-действия:

1. Проверить доверенный контекст, размер/структуру ввода; начать транзакцию и захватить guard.
2. Проверить receipt/токен/event. Принятый повтор вернуть без новых событий и версий.
3. Загрузить актуальные объекты. Сравнить все expected_version и версии полного состава группы.
4. Проверить права на действие и переходы ARCH-004/005, совместимость, принадлежность записей.
5. Изменить строки, увеличить затронутые версии, добавить историю, receipt и notification_jobs.
6. Commit; только затем вернуть успех. Любая ошибка до commit откатывает всё.

| Действие | Атомарная граница |
| --- | --- |
| Новая заявка | Contact/Identity при необходимости + Inquiry/Terms + исходные снимки + token/event/receipt + история + job владельцу |
| Перенос одного | Закрытие исходного участия + создание целевого + статус + версии обеих прогулок/заявки + история/receipt; деньги неизменны |
| Перенос/закрытие группы | Проверка полного outcomes и всех исходных/целевых версий + все связи/статусы/планы + история/receipt; один отказ откатывает всю группу |
| Исправление завершения | Проверка состояния исторического Visit + void ошибочного PROVIDED + новый статус/связь + версии + история/receipt |
| Поступление/исправление | cash_note/correction + версия Inquiry и актуального Visit + история/receipt; статус услуги неизменен |
| Каталог | Изменённые строки + catalog_version; снимки прежних заявок неизменны |

Захват guard обязателен даже при одиночном изменении. Проверка версии до его получения
не заменяет проверку после. Блокировка не заменяет ожидания клиента: устаревшая вкладка
получает VERSION_CONFLICT, а не автоматический повтор с новыми версиями.
При deadlock/timeout вся транзакция отменяется; bounded retry допустим с тем же ключом
и первоначальными ожиданиями. Неопределённый commit проверяется повтором, а не новым ключом.

VisitDetail, InquiryDetail, каталог и одна страница календаря читаются одним SQL-снимком
либо в READ ONLY REPEATABLE READ транзакции; несколько SELECT в обычном READ COMMITTED
не считаются согласованным снимком. См. [PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html).
Сессия чтения не держится между HTTP-страницами. Курсор задаёт стабильную сортировку
(received_at,id) для заявок и (start_at,id) для прогулок, привязан к фильтрам.
При изменениях расписания между страницами UI должен обновить диапазон; постраничное
чтение не обещает общий снимок во времени. Полный VisitDetail перечитывается перед групповой командой.
Закрытые прогулки не теряют исторический состав: текущие количества и оказанные/бывшие
участия отображляются отдельно, чтобы завершённая прогулка не выглядела пустой.

## 8. Уведомления и сессии

notification_jobs: id PK, origin_event_id FK, inquiry_id FK, recipient_ref, kind,
status, attempt_count, next_attempt_at, lease_token NULL, lease_until NULL,
last_error_code NULL, delivered_at NULL, payload_schema_version.
UNIQUE(origin_event_id,recipient_ref,kind). Полезная нагрузка минимальна; точные виды,
адресат и правила повторов принимает ARCH-007. Тексты/контакты не копируются в last_error.

Запись job входит в бизнес-commit. Доставщик коротко захватывает подходящую строку,
назначает аренду и commit; затем обращается к платформе вне транзакции. Результат обновляет
только при совпадении lease_token. Потерянный ответ платформы может дать повтор сообщения,
но не повторную заявку. Сбой доставщика не откатывает Inquiry. Его изменения доставки
не увеличивают версии бизнес-плана: notification_summary — оперативная сводка, не условие
групповых команд. Семантика delivered не означает прочтение владельцем.

owner_accounts: id PK, login UNIQUE, password_hash, disabled_at NULL, credentials_version.
owner_sessions: token_digest PK, owner_id FK, credentials_version, csrf_secret,
created_at, last_seen_at, expires_at, revoked_at NULL. Сырые session cookies не хранятся.
Смена credentials_version отзывает прежние сессии; подробности криптографии и auth-тесты
принадлежат реализации ARCH-005. При входе нет возможности создать роль из поля клиента.

## 9. Индексы, хранение и эксплуатация

Минимальные индексы помимо PK/UNIQUE/FK:

- inquiries(received_at,id), inquiries(status,received_at,id), inquiries(contact_id).
- visits(start_at,id), visits(status,start_at,id). Пересечение диапазона учитывает длительность,
  при NULL выбирается по началу; индекс не вводит запрета пересечений календаря.
- visit_participations(visit_id,closed_at), (inquiry_id,joined_at,id); уникальность активного участия выше.
- cash_notes(inquiry_id,recorded_at,id); corrections по original_note_id уже UNIQUE.
- event_inquiries(inquiry_id,event_id), event_visits(visit_id,event_id).
- notification_jobs(status,next_attempt_at,id); drafts(expires_at) для открытых; sessions(expires_at).

Индекс не является обещанием производительности: EXPLAIN и нагрузочная проверка выполняются
после реализации запросов. Партиционирование/кеш/материализованные денежные сводки не нужны сейчас.

Технические начальные сроки: неиспользованный токен 24 часа по API, черновик 7 дней после
последнего принятого ответа; после истечения ответы удаляются, повтор старого события не
восстанавливает их. Полный административный receipt хранится 30 дней, затем остаются digest,
область, нормализация и отметка использования для 410. Это срок повторного ответа, не срок
хранения заявки. Защита использованных токенов/event/ключей сохраняется без автоматического TTL.
Безопасная публичная квитанция и результат канальной подачи доступны до очистки связанной
заявки; для них result_expires_at=NULL. Связи receipt_inquiries охватывают все заявки,
чьи данные вошли в результат, включая групповой ответ. Очистка любой из них удаляет
полный результат этой операции, сохраняя техническую защиту от повторного выполнения.

Удаление заявки/контактов, аудит денежных записей и срок резервных копий требуют отдельной
политики владельца перед реальными данными. Сейчас бизнес-данные автоматически не удаляются.
Очистка персональных данных должна охватывать snapshots, changes, drafts, receipts, payload
доставки, связанные identity и копии; отмена заявки не является её удалением. При очистке
сначала tombstone всех связанных receipts и запрет новых jobs, затем редактирование/удаление
персональных полей в одной контролируемой процедуре под guard. Гонка с уже отправляемым
уведомлением требует остановки/отзыва аренды доставщика до очистки; отправленное сообщение
не исчезает автоматически. Digest-записи технически псевдонимизированы, не объявляются
юридически анонимными. Диагностические логи без клиентского текста: начальный TTL 14 дней.

Рабочие файлы PostgreSQL нельзя размещать в синхронизируемой OneDrive-папке репозитория.
Путь, резервное копирование и восстановление проверяются отдельной задачей окружения;
в Git только миграции и синтетические seed. Перед реальным пилотом нужен успешный тест
восстановления из копии, включая guard, receipts и историю, без повторной отправки старых jobs.
Восстановление копии может потерять новые ключи дедупликации: запуск внешних входов после
него требует сверки потерянного интервала, а не обещания защиты от всех прежних повторов.

## 10. Проверка перед реализацией и следующий этап

Ниже обязательные будущие интеграционные проверки на PostgreSQL, не уже выполненные тесты:

| Проверка | Ожидаемый результат |
| --- | --- |
| Два одновременных одинаковых submit | Одна заявка, один receipt и один логический job |
| Другой ключ того же токена; другой payload | Прежняя квитанция либо 409, без дубля |
| Сбой до commit / потеря ответа после commit | Полный rollback / восстановление прежнего результата |
| Новая заявка участника во время команды группы | Сериализация; устаревший состав получает VERSION_CONFLICT |
| Перенос одной заявки и параллельная отметка денег | Конфликт версии без потери денег/плана |
| Два активных участия одной заявки прямым SQL | Отказ UNIQUE |
| Две коррекции одного оригинала | Одна коррекция; другая — конфликт; суммы не удваиваются |
| Подтверждение без предоплаты; завершение с остатком | Успех, денежные строки не изменены |
| Частично оказанная группа / исправление единственного оказания | Отмена группы запрещена; исправление требует корректного состояния Visit |
| Неизвестные цена и длительность | NULL, нет выдуманного остатка/окончания |
| Изменение прайса/контакта/числа участников | Исходные и закрытые снимки сохранены; версия общего снимка обновлена |
| Устаревшее событие бота после reset/expiry | Новый шаг не исполняется, заявка не дублируется |
| Receipt после очистки результата | 410, не повтор команды; контакты не раскрываются |
| Завершённая прогулка и согласованное чтение | Историческое оказание видно; DTO не смешивает разные версии |
| Возврат больше поступлений / переплата / большие суммы | Факты сохранены, предупреждение/точный расчёт без переполнения |
| Недоступна платформа / истекла аренда доставщика | Заявка сохранена; устаревший worker не подтверждает новую аренду |

Приёмка ARCH-006: схема прослеживается к ARCH-003/005, определены SQL-ограничения и
отдельно прикладные инварианты, транзакции/повторы/история, ограничения очистки и восстановления.
Следующий ARCH-007 определяет уведомления владельцу. Затем отдельные ограниченные задачи
могут поручаться локальному воркеру: миграции и репозитории по этой схеме с облачным review.
Изменять бизнес-переходы, правила допуска или финансовые условия при реализации нельзя.
