# API MVP: границы и контракты v1

Status: ACCEPTED
Задача: ARCH-005; уточнение ARCH-008. Версия: 1.1. Дата: 2026-09-13.
Основание: [требования](requirements.md), [контекст](architecture.md),
[домен](domain-model.md), [переходы](booking-flow.md).
Это нормативный проект API; маршруты пока не реализованы. OpenAPI и код общих DTO
добавляются отдельной задачей в packages/contracts после принятия схемы ARCH-006.

## 1. Поверхности API

| Поверхность | Вызывающая сторона | Полномочия |
| --- | --- | --- |
| /api/v1/public/* | Браузер клиента | Каталог/правила, подача заявки, квитанция о приёме без доступа к CRM |
| Прикладной ChannelGateway | Доверенный адаптер Telegram/VK | Каталог, состояние своего диалога, подача нормализованной заявки |
| /api/v1/admin/* | Авторизованный владелец в CRM | Просмотр заявок/календаря и явные команды управления |
| Входы событий Telegram/VK | Внешние платформы | Только приём проверенного события соответствующим адаптером |

ChannelGateway — внутренний интерфейс приложения, не публичный HTTP endpoint.
Размещение ботов в другом процессе потребует отдельной аутентификации сервисов;
административная сессия владельца для этого не используется.
Точные URL/формат внешних событий, SDK, способ доставки событий и проверки подлинности
платформ не зафиксированы: официальные API и реальные аккаунты проверяются перед
реализацией адаптеров. Их payload не становится общим контрактом CRM.

## 2. Общие соглашения

- JSON в UTF-8. Успех: {"data": ...}; ошибка: {"error": {...}}. Успешная команда создания
  возвращает 201, остальные команды — 200. GET не изменяет бизнес-состояние.
- ID — непрозрачная строка до 128 символов, не телефон/имя; наружу не обещается SQL ID.
- Версия изменяемого объекта — целое положительное число. Клиент не назначает новую версию.
- Время фактов — строка с UTC offset; ответ нормализуется в UTC. Желаемая локальная дата
  YYYY-MM-DD и пожелание времени не преобразуются в точный момент автоматически.
- club_timezone — явный IANA-идентификатор конфигурации; публикуется вместе с каталогом.
  Значение для клуба подтверждается до запуска. Фиксированный offset не заменяет настройку зоны.
- Money — целое число копеек RUB, диапазон 0..9000000000000; null = неизвестно.
  Это технический диапазон представления, не лимит стоимости услуги. Для поступлений сумма > 0.
- Отсутствующий ключ PATCH-подобного payload = сохранить; null = явно очистить только
  поле, которое допускает неизвестность. Пустая строка не заменяет null.
- Неизвестные поля входных DTO отклоняются: нельзя молча принять подставленный status/paid.
  Произвольные клиентские значения никогда не назначают автора или служебный источник.
- Лимиты формы: имя 1..120 символов, контакт 1..200, пожелание времени 0..200,
  комментарий 0..2000, причина изменения 1..500, одно тело запроса до 32 KiB.
  Технический размер тела отдельной групповой команды до 256 KiB. Большой пакет получает
  явный отказ, не разбивается на частичные операции. Лимиты конфигурируемы, не ограничивают вместимость прогулки.
- participants_count — положительное целое до 2147483647, не предельная вместимость клуба.
  Допуск и реальную загрузку определяет владелец; отрицательные/дробные значения технически невалидны.
- Приватные ответы и квитанции приёма: Cache-Control: no-store. Логи не содержат пароли,
  токены, полный контакт/комментарий или сырые сообщения мессенджера.

## 3. Авторизация владельца

Один административный аккаунт. Нет публичной регистрации, восстановления через бота,
общего публичного API-key или назначения владельца по входному полю role.
Создание/восстановление аккаунта — контролируемая операция развёртывания, не открытый endpoint.

Предпочтительная схема для MVP: CRM и её API под одним origin, серверная сессия в cookie
с Secure, HttpOnly, SameSite=Lax, Path=/ и без Domain. Lax позволяет открыть закрытую
ссылку на карточку из мессенджера; сам GET ничего не изменяет. Сессию не хранить в localStorage.
При входе идентификатор сессии обновляется, при выходе/смене учётных данных отзывается.
Проверка сессии выполняется сервером для каждой закрытой операции.

| Метод и путь | Запрос | Ответ |
| --- | --- | --- |
| POST /api/v1/admin/session | login, password | 200: owner_id, csrf_token, expires_at; cookie сессии; общий 401 без раскрытия существования логина |
| GET /api/v1/admin/session | Cookie | owner_id, csrf_token, expires_at либо 401 |
| DELETE /api/v1/admin/session | Cookie, X-CSRF-Token | 200: signed_out=true, сессия отозвана |

Для изменяющих запросов проверяются Origin и тип JSON; после входа дополнительно
X-CSRF-Token, привязанный к сессии. Login допускается только с доверенного origin,
JSON и специальным X-Requested-With: crm; неизвестный/отсутствующий origin браузерного
login отклоняется. Кросс-origin доступ к admin не включается wildcard/CORS-отражением.
Публичная форма использует свой origin, бот — другой доверительный механизм адаптера.
Idempotency-Key не заменяет проверку сессии, CSRF и прав.

Безопасная реализация паролей/сессий, rate limits входа, сроки бездействия/жизни и
восстановление аккаунта требуют отдельной auth-задачи и проверок до выпуска;
этот документ не является доказательством реализованной защиты.
Основание: [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
и [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## 4. Публичный каталог и заявка

### Чтение

GET /api/v1/public/catalog возвращает Catalog:

- catalog_version, club_timezone, contact_info, location_link, visit_rules.
- services[]: id, title, description, information, options[].
- options[]: id, duration_minutes (null для согласования), pricing_mode
  FIXED_PER_PERSON/NEGOTIATED, price_minor (null для NEGOTIATED), currency=RUB.

Выдаются только доступные для новых обращений варианты. Исторические скрытые варианты
видны в собственных снимках заявок CRM. Одни и те же сведения читаются внутренними адаптерами.
Изменение контента владельцем может идти через управляемую конфигурацию на первом этапе;
редактор каталога и произвольная CMS не добавляются этим API автоматически.

### Подача

POST /api/v1/public/submission-tokens, пустой JSON: 201 с submission_token и expires_at.
Короткоживущий непрозрачный токен одной подачи выдаётся сервером; срок приёма нового
действия публикуется в expires_at (начальный технический параметр — 24 часа).
Выдача и приём имеют отдельное ограничение частоты от злоупотребления.
Токен не является согласием на условия или аутентификацией клиента.

POST /api/v1/public/inquiries требует Idempotency-Key и submission_token в теле.
UI создаёт случайный ключ на явную отправку, сохраняет его/токен до определённого результата
и использует те же значения при сетевом повторе. Пример:

```json
{
  "submission_token": "synthetic-submission-token",
  "catalog_version": 3,
  "service_option_id": "group-60",
  "requester": {"name": "Тестовый клиент", "contact": {"kind": "PHONE", "value": "+70000000000"}},
  "participants_count": 2,
  "requested_time": {"date": "2026-10-01", "time_text": "после 14:00"},
  "experience": "BEGINNER",
  "comment": "Синтетический пример",
  "acquisition": {"utm_source": "example", "utm_medium": "link", "utm_campaign": "autumn"}
}
```

Обязательны token, catalog_version, service_option_id, requester с доступным контактом,
participants_count, requested_time.date. time_text/comment/experience/acquisition необязательны.
acquisition принимает utm_source/utm_medium/utm_campaign/utm_content/utm_term до 200 символов
каждая. Неизвестные метки и некорректные значения внутри acquisition отбрасываются без
отказа в заявке; это явное исключение из строгого DTO, не разрешение служебных полей.
Контакт kind=PHONE/TELEGRAM/VK; строка — способ связи со слов клиента, не проверенная
идентичность/право на чужую карточку. experience=BEGINNER/EXPERIENCED/UNKNOWN; отсутствие = UNKNOWN.
Поля веса/возраста не обязательны и не вводят автоматический допуск. Контакт/текст проверяются
по формату и размеру, без обогащения внешними сервисами или автоматического слияния клиентов.

```json
{"data":{"receipt_id":"opaque-receipt","received":true,"booking_confirmed":false}}
```

Публичный ответ не содержит клиентские данные, внутренний финансовый статус или доступ
к списку заявок. Публичного GET заявки по ID/телефону нет. Потерянный ответ восстанавливается
повтором POST с тем же ключом/токеном. receipt_id — только номер обращения, не bearer-доступ в CRM.
Квитанция описывает момент приёма; booking_confirmed=false в повторе не сообщает текущий
статус записи, которую владелец мог уже подтвердить.
Если цена изменилась, но вариант доступен, запрос принимается с новой достоверной
каталожной справкой и отметкой для владельца о несовпадении версии; старую цену клиента
нельзя считать согласованным итогом. При скрытом/неизвестном варианте — 409 OPTION_UNAVAILABLE
без создания заявки, клиенту предлагается обновить каталог.

Один submission_token привязывается максимум к одной принятой заявке. При другом ключе
на уже использованный токен: прежняя безопасная квитанция только при том же payload,
иначе 409 SUBMISSION_ALREADY_USED. Токен/ключ не раскрывают контакты даже при повторе.
После истечения срока неиспользованного токена — 410 SUBMISSION_EXPIRED, новая подача требует
нового токена. Для использованного токена результат повторяется независимо от срока нового
приёма; при удалении персональной заявки остаётся технический tombstone без контактов,
и ответ — 410 RECEIPT_EXPIRED, а не создание дубля. Политика хранения — ARCH-006.

## 5. Общий интерфейс ботов

Адаптер передаёт в ChannelGateway доверенный ChannelContext:
platform=TELEGRAM/VK, integration_id, external_sender_id, conversation_id, event_id.
ID строки непрозрачны. Payload пользователя не может подменить этот контекст.

| Операция | Данные | Результат |
| --- | --- | --- |
| ReadCatalog | ChannelContext | Тот же Catalog |
| ReadDraft | Контекст диалога | answers, step, version, expires_at либо отсутствие черновика |
| SaveDraft | expected_version, answers, step, event_id | Новая версия; не создаёт заявку |
| SubmitInquiry | Бизнес-поля формы без submission_token; контакт может быть доверенной идентичностью канала; draft_version и submit_event_id | Безопасная квитанция о приёме и внутренний inquiry_id для доставки, не публикуемый произвольно |
| ResetDraft | expected_version, event_id | Черновик закрыт; принятые заявки не отменены |

Идентичность отправки включает платформу, integration_id и идентичность конкретного
финального действия, а не только sender/chat. Повтор исходного события после изменения
шага не трактуется как ответ нового шага. Адаптер обрабатывает переходы последовательно
в пределах диалога с проверкой версии; сериализация/журнал событий — ARCH-006.
Контакт из Telegram нельзя использовать для чтения заявки из VK без административных прав.
Переход сайт → бот может передавать только разрешённую метку кампании/корреляции;
нельзя вкладывать в публичную ссылку телефон, содержимое заявки или admin session.
Форматы deep links и подтверждений внешних событий проверяются до реализации адаптеров.

## 6. Чтение CRM и DTO

| Метод и путь | Параметры | Результат |
| --- | --- | --- |
| GET /api/v1/admin/inquiries | status, has_visit, channel, cursor, limit | items: InquirySummary[], next_cursor |
| GET /api/v1/admin/inquiries/{id} | — | InquiryDetail |
| GET /api/v1/admin/visits | from, to (UTC-моменты), cursor, limit | VisitSummary[] и next_cursor; календарь обязан дочитать все страницы |
| GET /api/v1/admin/visits/{id} | — | VisitDetail: план, все актуальные участия, версии затрагиваемых заявок |
| GET /api/v1/admin/inquiries/{id}/history | cursor, limit | События изменений этой заявки без секретов |
| GET /api/v1/admin/visits/{id}/history | cursor, limit | Изменения общего плана и состава |

limit по умолчанию 50, диапазон 1..100; стабильная сортировка с ID как дополнительным
ключом, cursor непрозрачен и привязан к фильтрам. from включительно, to исключительно.
Выбираются пересекающие интервал посещения, не только начинающиеся внутри; неизвестная
длительность фильтруется по началу и возвращается как unknown, без выдуманного окончания.
Календарь использует часовой пояс клуба для формирования интервала. Большой диапазон
может дать 422 RANGE_TOO_LARGE (начальная техническая граница 93 дня на запрос),
но записи внутри него не обрезаются молча. Незапланированные заявки доступны через has_visit=false.

InquirySummary: id, version, status, requester_name, service_title, participants_count,
requested_time, visit_id/null, agreed_start_at/null, received_at, channel, cash_summary.
InquiryDetail добавляет contact_snapshot, current_contact, selected_option_snapshot,
agreed_terms, comment, owner_note, participation/null, acquisition, cash_notes[],
notification_summary, allowed_commands[]. Исторические закрытые участия доступны через history.

AgreedTerms: service_option_id, participants_count, duration_minutes/null,
total_minor/null, expected_prepayment_minor/null, currency=RUB, note.
VisitSummary: id, version, status, service_title, start_at, duration_minutes/null,
end_at/null, inquiry_count, participants_count, has_unresolved_inquiries.
VisitDetail добавляет актуальные participations[]: id, inquiry_id, inquiry_version,
status, participants_count, requester_name, cash_summary; и allowed_commands[].
Чтение VisitDetail должно дать согласованный снимок состава/версий, а не смесь разных моментов.
При слишком большом detail — явная ошибка/альтернативный workflow, не обрезанный список для команды.

allowed_commands — подсказка UI, не разрешение: сервер повторно проверяет права и условия.
Персональные данные каждого заявителя доступны только владельцу; бот не получает список группы.

## 7. Общий протокол команд

Все изменения CRM, кроме session, требуют Idempotency-Key. Создание нового объекта без
исходной версии допустимо; для изменения существующего обязательно expected_version.
Одинаковый ключ в области owner_id + method + canonical path означает одно действие.
Сначала проверяются права/CSRF, затем находится принятый повтор, затем для нового действия
проверяются версии и бизнес-условия. Поэтому принятый повтор не ломается из-за увеличения версии.

У ключа фиксируется нормализованный семантический payload. Тот же ключ с другим payload —
409 IDEMPOTENCY_MISMATCH. Операция в работе — 409 REQUEST_IN_PROGRESS с указанием повторить
тот же ключ; после неопределённого сетевого результата нельзя автоматически создавать новый ключ.
При первом успехе 201/200; повтор завершённого успеха — 200 и Idempotent-Replay: true,
с тем же результатом, без новой истории/денежной отметки/задания доставки.
История успешного действия и связь ключа с ним записываются согласованно с изменениями.
После очистки старого результата сохраняется запись использованного ключа: 410 RESULT_EXPIRED,
не повторное выполнение. Ошибки до принятия изменений не расходуют ключ; 500/503 требуют
проверки прежнего ключа, так как внешний ответ не доказывает отсутствие сохранения.

POST /api/v1/admin/inquiries — ручной ввод владельцем: данные заявки, source_kind
PHONE/WHATSAPP/OTHER, owner_note; NEW. Проверенный канал бота вручную не подделывается.
Поля: service_option_id, requester, participants_count, requested_time/null, experience,
comment, owner_note, source_kind. submission_token и catalog_version публичной формы
не нужны: действуют административная сессия и Idempotency-Key, снимок каталога берётся
сервером. Неизвестное пожелание даты при ручном вводе допускает null; это не подтверждение.
POST /api/v1/admin/visits — {service_id, start_at, duration_minutes:null|positive_int};
создаёт PLANNED, версия 1; пустая прогулка явно обозначается.

POST /api/v1/admin/inquiries/{id}/commands:

```json
{
  "type":"CONFIRM",
  "expected_version":4,
  "expected_visit_versions":{"visit-example":2},
  "payload":{"visit_id":"visit-example"}
}
```

У команды строгий payload по type; произвольный PATCH status или is_paid отсутствует.
expected_visit_versions содержит версии всех затронутых исходных/целевых посещений.
Участия изменяют версии Inquiry и Visit; статус/число людей/условия связанной заявки
также обновляют версию Visit, если затронут групповой снимок. Нехватка ожидаемой версии —
422 EXPECTED_VERSION_REQUIRED; несовпадение — 409 VERSION_CONFLICT без частичных изменений.

Результат: command_id, inquiry (обновлённый InquiryDetail), changed_visits[] с ID/версиями.
При общегрупповой команде возвращаются visit и changed_inquiries[] с ID/версиями;
клиент перечитывает детали. Состав результата одинаков для первого ответа и повтора.

## 8. Команды заявки

| type | payload | Поведение |
| --- | --- | --- |
| START_NEGOTIATION | {} | NEW → NEGOTIATING |
| UPDATE_DETAILS | changes: name/contact/requested_time/comment/owner_note; reason при исправлении истории | Только перечисленные поля, не статус и не идентичность внешней платформы |
| UPDATE_TERMS | changes: поля AgreedTerms; reason | Условия задаёт владелец, деньги не переписываются; при влиянии на группу проверяются версии Visit |
| ASSIGN_VISIT | visit_id, reason | NEW → NEGOTIATING; NEGOTIATING остаётся; предварительное участие, если его ещё нет; перенос существующего — MOVE |
| CONFIRM | visit_id | NEW/NEGOTIATING → CONFIRMED; создаёт/использует единственное актуальное участие; деньги и известная цена не обязательны |
| RETURN_TO_NEGOTIATION | reason, keep_visit:bool | CONFIRMED → NEGOTIATING; план сохраняется предварительно или связь закрывается |
| MOVE | target_visit_id, confirmed:bool, reason | Перенос актуального участия; CONFIRMED при явном подтверждении, иначе NEGOTIATING |
| UNSCHEDULE | reason | Закрывает актуальное участие, NEW/NEGOTIATING/CONFIRMED → NEGOTIATING без плана |
| COMPLETE | {} | CONFIRMED → COMPLETED; участие закрывается как оказанное; нет условия полной оплаты |
| CONFIRM_AND_COMPLETE | visit_id | Явное комбинированное действие для NEW/NEGOTIATING с проверкой обеих операций и двумя записями истории |
| CANCEL | reason | NEW/NEGOTIATING/CONFIRMED → CANCELLED, актуальная связь закрыта; деньги не меняются |
| REOPEN | reason | CANCELLED → NEGOTIATING, без автоматического возврата в прежнюю группу |
| CORRECT_COMPLETION | target:CONFIRMED/NEGOTIATING, visit_id/null, reason | Исправление ошибочного COMPLETED; для CONFIRMED нужен валидный PLANNED-план, версия и новая актуальная связь |

MOVE/UNSCHEDULE/ASSIGN не применяются к COMPLETED/CANCELLED как обход REOPEN/исправления.
CONFIRM не может незаметно заменить другую актуальную прогулку: 409 PARTICIPATION_CONFLICT,
сначала явный MOVE. Совместимость варианта/длительности владелец согласует до назначения;
расхождение общей длительности возвращается как 409 PLAN_CONFLICT, а не молча выравнивается.
Если согласованная длительность неизвестна, это явно видно, не маскируется совпадением.
UPDATE_TERMS не назначает отрицательные суммы. Ноль — конкретная сумма, а не неизвестная
цена; сценарий бесплатной услуги остаётся вне согласованного MVP и требует отдельного
решения перед реализацией, как указано в доменной модели. Этот контракт не вводит для
него новое бизнес-правило. null допустим и не препятствует CONFIRM/COMPLETE.
Оплата не служит условием допуска.

## 9. Команды общей прогулки

POST /api/v1/admin/visits/{id}/commands требует type, expected_version,
expected_inquiry_versions (полная карта затронутых заявок), expected_target_visit_versions,
payload. Version Visit защищает также состав группы: неизвестная добавленная/удалённая заявка
вызывает конфликт. Отсутствие целевой версии нельзя компенсировать чтением backend без проверки ожиданий.

| type | payload | Условие |
| --- | --- | --- |
| RESCHEDULE | start_at, duration_minutes/null, outcomes[] | Только PLANNED; по каждой актуальной заявке CONFIRMED_HERE, NEGOTIATING_HERE, MOVE или UNSCHEDULE |
| CANCEL_VISIT | reason, outcomes[] | Только PLANNED, фактически оказанных участий нет; каждой актуальной заявке CANCEL, MOVE или UNSCHEDULE |
| COMPLETE_VISIT | outcomes[] | Только PLANNED; каждой актуальной заявке COMPLETE, CANCEL (например неявка), MOVE или UNSCHEDULE; есть хотя бы одно оказание с учётом истории |
| REOPEN_VISIT | reason, start_at, duration_minutes/null | Явное исправление закрытого Visit → PLANNED; историю и исходы заявок не откатывает, участия не восстанавливает |

Outcome = {inquiry_id, action, target_visit_id? , confirmed? , reason?}.
Каждая актуальная заявка присутствует ровно один раз; посторонние/повторные ID и неполный
список отклоняются. Для MOVE обязательно указать target_visit_id и confirmed; для CANCEL,
MOVE, UNSCHEDULE — reason. COMPLETE применим только к CONFIRMED; для неподтверждённого
участия владелец сначала явно подтверждает его отдельной командой.
Все исходные и целевые объекты проверяются до изменения; одна транзакция либо явный отказ.
Физическая стратегия блокировок определяется ARCH-006. Нет автоматического разбиения пакета.

Пустой PLANNED Visit можно отменить с outcomes:[]; нельзя завершить как оказанный без
исторического оказания. При частичном фактическом оказании CANCEL_VISIT отклоняется;
владелец использует COMPLETE_VISIT с разными исходами оставшихся заявок.
REOPEN_VISIT не скрывает прошлые оказания; дальнейшая отмена по-прежнему их учитывает,
пока владелец отдельно не исправил ошибочный факт. Новый реальный сеанс — новый Visit.

## 10. Ручные отметки денег в карточке

POST /api/v1/admin/inquiries/{id}/cash-notes: expected_version, kind,
amount_minor, occurred_at, note; kind=RECEIPT/REFUND_NOTE.
RECEIPT — владелец подтверждает полученное; REFUND_NOTE — уже состоявшийся возврат,
введённый вручную, а не приказ вернуть. Только положительные точные суммы и RUB.
Усложнённого согласования, invoice, checkout, банковских webhooks и платёжных статусов нет.

Исправление: POST /api/v1/admin/inquiries/{id}/cash-notes/{note_id}/corrections
с expected_version, reason, replacement:null|{kind,amount_minor,occurred_at,note}.
Оригинал остаётся историческим; null помечает ошибочную запись неактуальной, replacement
создаёт её исправленную версию. Повторное исправление неактуального оригинала — 409
CASH_NOTE_SUPERSEDED. История автора/времени серверная; свободного DELETE сумм нет.
Эти записи доступны и после CANCELLED/COMPLETED, не меняют бизнес-статус заявки.
Оба запроса также принимают expected_visit_versions для актуального участия, если оно
есть. Денежная сводка входит в VisitDetail: изменение отметки увеличивает версии заявки
и её актуального Visit в одной транзакции. Устаревшая команда группы получает конфликт;
при отсутствии актуального участия достаточно expected_version заявки.

CashSummary: received_minor, returned_minor, net_received_minor, total_minor/null,
balance_minor/null, calculation_warning/null. net = сумма действующих RECEIPT − REFUND_NOTE;
balance = total − net при известном total. Если возвращённое больше полученного,
система сохраняет явно введённые факты, но показывает DATA_REVIEW_REQUIRED, не скрывает разницу.
После CANCELLED balance не называется задолженностью и не предъявляется клиенту.
Планируемый возврат — заметка владельца, не REFUND_NOTE до фактического действия.

Ожидаемая предоплата задаётся UPDATE_TERMS. UI может предложить 50% известного итога;
округление половины копейки для подсказки — вверх до целой копейки (ROUND_HALF_UP для
неотрицательных сумм). Владелец подтверждает/меняет значение. При изменении итога
предоплата не переписывается автоматически; это не обязательство оплатить перед CONFIRMED.

## 11. Ошибки и повторяемое поведение

```json
{"error":{"code":"VERSION_CONFLICT","message":"Данные изменены. Обновите карточку.","request_id":"trace-example","details":{"resource":"inquiry","current_version":8},"fields":[]}}
```

| HTTP | code | Клиентское действие |
| --- | --- | --- |
| 400 | INVALID_JSON | Исправить сериализацию |
| 401 | AUTH_REQUIRED | Войти; отложенная команда после входа повторяется с прежним ключом |
| 403 | FORBIDDEN / CSRF_FAILED | Не повторять молча; обновить сессию/права |
| 404 | NOT_FOUND | Объект недоступен/не существует; детали приватных объектов не раскрываются публично |
| 409 | VERSION_CONFLICT / PARTICIPATION_CONFLICT / PLAN_CONFLICT | Перечитать затронутые объекты, получить новое решение владельца |
| 409 | INVALID_TRANSITION / GROUP_OUTCOMES_INCOMPLETE | Исправить действие, не назначать status напрямую |
| 409 | IDEMPOTENCY_MISMATCH / SUBMISSION_ALREADY_USED | Не заменять автоматически ключ ради повтора другого действия |
| 409 | REQUEST_IN_PROGRESS | Повторить тот же запрос/ключ с задержкой |
| 410 | SUBMISSION_EXPIRED / RESULT_EXPIRED / RECEIPT_EXPIRED | Следовать правилам конкретного токена; не повторять уже принятую команду новым ключом |
| 413 | PAYLOAD_TOO_LARGE | Уменьшить ввод; групповую транзакцию не дробить молча |
| 415 | UNSUPPORTED_MEDIA_TYPE | Передать application/json |
| 422 | VALIDATION_ERROR / EXPECTED_VERSION_REQUIRED / RANGE_TOO_LARGE | Показать ошибки полей/параметров |
| 429 | RATE_LIMITED | Уважать Retry-After; данные формы сохранить |
| 503 | TEMPORARILY_UNAVAILABLE | Сохранить ввод/ключ; повторить прежний запрос |

Список codes включает также OPTION_UNAVAILABLE и CASH_NOTE_SUPERSEDED
из соответствующих разделов. Клиент не анализирует русский message
как машинное условие. details для публичного API не содержат контакты, сырые исключения,
таблицы/SQL или административные версии чужих объектов. 500 не раскрывает stack trace.

## 12. Приёмка контрактов и передача

Проверить при реализации: публичный ввод служебных полей отклонён; приём заявки не
подтверждает время; оба бота используют одну операцию; публичного чтения CRM нет;
повтор после потери ответа не дублирует заявку/ручную сумму; старые версии отклонены;
перенос группы атомарен; отсутствие предоплаты не мешает CONFIRM и остаток не мешает
COMPLETE; CANCEL не переводит денег; UNKNOWN цена не превращается в ноль; календарь
не скрывает страницы и отделяет неизвестную длительность; неизвестная метка рекламы
не мешает приёму; клиентам группы не раскрываются контакты остальных.

ARCH-006 уточняет физическую схему, ограничения, записи повторов/истории и транзакционные
блокировки; ARCH-007 — канал, адресат и повтор уведомления владельцу. Очистка персональных
данных должна сохранять обезличенную защиту от повторного выполнения использованного ключа.
TTL черновиков, технических записей и диагностических логов фиксируются до реализации очистки.
Изменение обязательных DTO/enum/семантики v1 требует отдельного cloud review общих контрактов;
локальный воркер реализует только ограниченные задачи по принятому договору.
Сервисы аналитики и клиентские напоминания отдельно не подключены и не обещаны.

## 13. Операторские команды доставки

Уточнение ARCH-008: закрытая поверхность admin для владельца. Это принятый контракт,
не реализованные маршруты. Общие cookie/CSRF, строгие DTO, ошибки и Idempotency-Key
действуют так же, как в разделах 3/7. Адресат не задаётся сырым chat_id или URL из запроса.

GET /api/v1/admin/notification-jobs/{id} возвращает id, version, inquiry_id, status,
recipient_ref, attempt_count, cycle_no, cycle_attempt_count, cycle_started_at,
next_attempt_at, delivered_at/null, safe_error_code/null, allowed_commands[].
Сырых токенов, chat_id, тела ответа платформы и клиентских комментариев нет.
InquiryDetail.notification_summary включает job_id и version для перехода к этим данным.
404/401/403 не раскрывают состояние доставки публичному клиенту.

POST /api/v1/admin/notification-jobs/{id}/commands:
type, expected_version, payload. reason обязателен (1..500 символов).

| type | payload | Допустимость и результат |
| --- | --- | --- |
| RETRY | reason | Только BLOCKED/FAILED, действующее проверенное назначение; тот же job, новый цикл PENDING, общий счётчик попыток сохранён |
| REASSIGN | recipient_ref, reason | Только BLOCKED/FAILED; цель отличается и существует в доверенной проверенной конфигурации; сохраняет состояние и бюджет, не начинает отправку |
| SUPPRESS | reason | PENDING/RETRY_WAIT/BLOCKED/FAILED → SUPPRESSED; цикл и история сохранены |

Все команды увеличивают version один раз, возвращают command_id и актуальный JobDetail,
создают receipt и аудит оператора атомарно. Повтор принятого ключа возвращает прежний
результат до проверки изменившейся версии, без нового цикла/события. Изменённый payload
с прежним ключом — IDEMPOTENCY_MISMATCH. После очистки результата — RESULT_EXPIRED.

SENDING → 409 DELIVERY_IN_PROGRESS; требуется завершение/восстановление аренды,
а не принудительный запуск второго отправителя. Несовпадение version → VERSION_CONFLICT.
SENT/SUPPRESSED не возобновляются этими командами. Недопустимый переход — INVALID_TRANSITION.
Неизвестное/непроверенное назначение — 409 RECIPIENT_NOT_READY; совпадающее REASSIGN —
422 VALIDATION_ERROR. Уникальность события/назначения нарушена — 409 NOTIFICATION_CONFLICT.
RETRY не обходит общий next_allowed_at и ограничение частоты платформы.

Создание и проверка конфигурации адресата — операция настройки окружения, а не публичный
или административный endpoint с произвольным чатом. REASSIGN не редактирует SENT и не
переносит молча всю очередь. Массовых команд и пользовательских напоминаний не добавлено.
Подавление останавливает будущие попытки, но не удаляет уже отправленные сообщения.
Эти правила должны быть проверены на PostgreSQL: конкуренция оператора с доставщиком,
повторы команд, перезапуск после исчерпания бюджета и сохранение общего rate limit.
