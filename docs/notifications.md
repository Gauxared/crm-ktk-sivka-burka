# Уведомления владельцу MVP

Status: ACCEPTED
Задача: ARCH-007; уточнение ARCH-008. Версия: 1.1. Дата: 2026-09-13.
Основание: [требования](requirements.md), [архитектура](architecture.md),
[API](api.md), [схема хранения](database.md), [жизненный цикл](booking-flow.md).
Это проект доставки, не подключённый бот. Реальные сообщения в этой задаче не отправляются.

## 1. Назначение и адресат

Уведомление помогает владельцу заметить новую заявку и открыть карточку для согласования.
CRM остаётся источником текущих данных, факта оплаты и статуса услуги.
Технический выбор MVP — Telegram для владельца, как предложено в D-01 требований;
клиентские заявки приходят из лендинга, Telegram и VK независимо от канала уведомления.
Личный Telegram-диалог владельца и конкретный бот проверяются при настройке пилота.
Это не утверждение, что адресат уже настроен или подтвердил тестовую доставку.

recipient_ref — неизменяемая версия назначения в доверенной конфигурации: интеграция
бота и проверенный личный chat_id владельца. Секрет токена хранится вне Git/прикладных
таблиц. Поле клиента, sender_id входящего события или ссылка рекламы не назначают адресата.
Первый написавший боту человек не становится владельцем. Общая группа получателей,
VK-резервирование, SMS/email и отдельные тренеры не подключаются в этом MVP.
Можно использовать клиентского Telegram-бота для отправки владельцу, но входы диалогов
и адрес назначения проверяются раздельно; административных команд в этом боте нет.

При смене chat_id старая версия recipient_ref не перенаправляется молча на новый чат.
Доставщик приостанавливается; оператор проверяет новое назначение и явно переносит
неотправленные задания с историей. SENT автоматически повторно не рассылаются.
Ротация токена того же бота не меняет идентичность адресата или логический ключ задания.

## 2. События

| Событие | Действие |
| --- | --- |
| Первое успешное принятие заявки с лендинга/Telegram/VK | Одно логическое OWNER_INQUIRY_RECEIVED для владельца |
| Первое создание заявки вручную владельцем | То же уведомление с пометкой «внесено вручную», единое правило новой заявки |
| Повтор принятого submit/команды | Возврат прежнего результата; новых заданий нет |
| Ответ на промежуточный вопрос бота, просмотр каталога, черновик | Уведомления владельцу нет |
| Владелец изменил время, условия, статус, деньги или состав группы | История в CRM; отдельное сообщение владельцу не создаётся |
| Ошибка доставки | Состояние в CRM/технической диагностике; сообщение через тот же сломанный канал не создаётся |

Единое правило для ручного ввода соответствует транзакции создания в ARCH-006; исключение
для ручных заявок можно отдельно изменить позднее, оно не выводится из источника автоматически.
Завершение/отмена/возобновление заявки не является повторным событием её поступления.
Две независимые заявки одной прогулки дают два уведомления с разными ID, без общей карточки
контактов в мессенджере. Новое реальное обращение прежнего клиента тоже даёт новое уведомление.

Подтверждение клиенту «заявка принята» — часть ответа формы/бота, не OWNER_INQUIRY_RECEIVED.
Ошибка отправки владельцу не меняет этот успешный результат. Автоматических подтверждений
записи, напоминаний клиенту, просьб об оплате или рекламных рассылок здесь нет.

## 3. Сообщение и ссылка

Один короткий plain-text шаблон, без LLM и клиентского Markdown/HTML. Включает:
ID заявки, канал, время поступления в зоне клуба, выбранную услугу/длительность,
количество участников, желаемую дату/время и закрытую ссылку на CRM.
Цена не называется согласованной, пожелание не называется подтверждённой записью.
Телефон, имя, свободный комментарий, сведения о весе/здоровье, оплаты и рекламные метки
остаются в CRM. Это уменьшает копирование клиентских данных в сообщения.

Пример на синтетических данных:

```text
Новая заявка № <inquiry_id> · VK
Получена: 01.10.2026, 10:15 (часовой пояс клуба)
Групповая прогулка · 60 минут · 2 участника
Пожелание: 03.10.2026, после 14:00
Это пожелание клиента; время согласует владелец.
Карточка: <доверенный CRM_ORIGIN>/inquiries/<inquiry_id>
```

Это проект UI-ссылки, не новый API endpoint. CRM_ORIGIN задаётся конфигурацией HTTPS,
проверяется при запуске, не берётся из Host заголовка публичного запроса. В URL нет
токена сессии, телефона или авторизации. Переход требует входа владельца; сохранённый
return path ограничен локальными маршрутами CRM, без открытого redirect.
Предпросмотр ссылки отключён. GET карточки не подтверждает запись и не отмечает оплату.

Шаблон строится по исходному снимку поступления, а не текущим изменённым условиям.
При поздней доставке явно добавляется «Уведомление о поступлении; актуальное состояние в CRM».
Время получения всегда видно. Даже после обработки заявки сообщение остаётся историческим
сигналом; автоматической отмены доставки по одному лишь статусу заявки нет.

Лимит приложения — 1500 символов; длинное пожелание безопасно обрезается с многоточием,
ID и ссылка сохраняются. Управляющие символы удаляются, переносы пользовательского текста
нормализуются; client input не может добавить кнопки или изменить адрес ссылки.
При недоступном исходном снимке из-за очистки персональных данных отправка подавляется,
а не восстанавливает удалённые данные из логов. Финальный текст не хранится в last_error.

## 4. Атомарная постановка и гарантии

В транзакции принятия сохраняются Inquiry, исходное событие истории, receipt и
notification_job с kind=OWNER_INQUIRY_RECEIVED и status=PENDING. Уникальность
(origin_event_id,recipient_ref,kind) гарантирует один логический job на это событие.
Бизнес-commit не ждёт внешнего HTTP-вызова. Rollback не оставляет задания на несуществующую заявку.
Сбой отправки не откатывает заявку, не меняет её статус/версию и не создаёт новый submit.

Если назначение ещё не настроено, сохраняется job для стабильного логического назначения
OWNER_PRIMARY_UNCONFIGURED в состоянии BLOCKED, причина CONFIG_MISSING. Позже оператор
явно связывает эти jobs с проверенной версией назначения; источник/история сохраняются.
Отсутствие конфигурации видимо в CRM, а не теряет заявку. Перед пилотом эта ситуация должна
быть устранена. Реализация переназначения проверяет UNIQUE в одной транзакции.

Гарантируется сохранение намерения доставки вместе с заявкой. Успешная внешняя доставка
при постоянной блокировке/недоступности не гарантируется. Возможны повторные попытки,
а при неопределённом результате — дубликаты сообщения. Exactly-once человеку не обещается.
Одинаковый ID заявки в повторном сообщении позволяет распознать дубль.

## 5. Состояния задания и аренда

| status | Значение и переход |
| --- | --- |
| PENDING | Готово к первой попытке после next_attempt_at; → SENDING |
| SENDING | Захвачено доставщиком; → SENT, RETRY_WAIT, BLOCKED или FAILED |
| RETRY_WAIT | Временная/неопределённая ошибка; после next_attempt_at → SENDING |
| SENT | Получен валидный успешный ответ платформы; автоматических повторов нет |
| BLOCKED | Требуется исправить конфигурацию/доступ; автоматических попыток нет |
| FAILED | Исчерпан бюджет повторов либо ошибка шаблона/контракта; требуется разбор |
| SUPPRESSED | Явно остановлено из-за очистки/решения оператора; причина сохранена |

SENT означает приём платформой, не прочтение владельцем. delivered_at ставится только при
валидном успехе. Потерянный ответ не выставляет delivered_at. notification_summary в CRM
отображает фактическое состояние, число попыток, время следующей и безопасный код ошибки.
Если неизвестно, успела ли платформа принять сообщение, показывается «результат неизвестен»;
это выводится из last_error_code=DELIVERY_UNCERTAIN, а не из статуса заявки.

Доставщик выбирает due-job по next_attempt_at,id, под блокировкой строки назначает
SENDING, новый случайный lease_token и lease_until, увеличивает attempt_count и commit.
Сетевой вызов идёт вне транзакции; результат сохраняется только условным UPDATE с тем же
lease_token и SENDING. Устаревший worker не может изменить состояние новой аренды.
Начальные технические настройки: одна внешняя отправка одновременно, HTTP timeout 15 s,
аренда 60 s, проверка очереди каждые 5 s. Между отправками одному адресату минимум 1 s;
ответ ограничения частоты платформы имеет приоритет над локальными интервалами.

Истёкшая аренда возвращается в RETRY_WAIT с DELIVERY_UNCERTAIN: процесс мог упасть после
отправки, но до записи результата. Восстановление аренды не обнуляет attempt_count.
Перед повтором снова проверяются назначение, подавление и доступность снимка.
Долгая остановка процесса не запускает пачку параллельных просроченных отправок.
В MVP развёртывается один доставщик. Чтобы случайный второй процесс не отправлял другие
jobs тому же адресату одновременно, требуется общая аренда назначения: таблица
notification_recipient_state(recipient_ref PK, lease_token NULL, lease_until NULL,
next_allowed_at). Аренда назначения и job захватываются одной короткой транзакцией,
в порядке назначение → job; общий бизнес-guard при этом не нужен. При rate limit
next_allowed_at обновляется для всего назначения, включая другие jobs. Поля и транзакции
согласованы в разделе 8 схемы БД (ARCH-008). После истечения аренды физическое завершение старого
сетевого вызова не гарантируется; fencing защищает запись результата, но не исключает
повтор на внешней стороне. Такой случай остаётся DELIVERY_UNCERTAIN.

## 6. Ошибки и повторы

Ниже параметры нашего доставщика, не обещания SLA платформы. Первая попытка сразу после
commit. После неудачных попыток интервалы: 30 s, 2 min, 10 min, 30 min, 2 h, 6 h, 12 h;
положительный jitter 0..20%. Максимум 8 захватов на цикл доставки и 48 часов с момента
постановки/явного перезапуска. Достижение любой границы → FAILED. Падение после захвата
тоже расходует попытку, чтобы бесконечные падения не создавали бесконечный цикл.

| Результат | Классификация |
| --- | --- |
| Валидный success с результатом отправки | SENT |
| Ограничение частоты | RETRY_WAIT; ждать не меньше retry_after и локального backoff |
| Сетевая ошибка до доказанной отправки, временная недоступность, 5xx | RETRY_WAIT |
| Timeout/обрыв/невалидный ответ после возможной отправки | RETRY_WAIT, DELIVERY_UNCERTAIN; возможен дубль |
| Недействительные credentials, запрещённая доставка, недоступный адресат | BLOCKED, без автоматического перебора других адресатов |
| Ошибка длины/формата/параметров нашего запроса | FAILED, TEMPLATE_INVALID/REQUEST_INVALID |
| Неизвестная ошибка | Ограниченный повтор, затем FAILED; никаких решений из текста пользователя |

Если retry_after выходит за границу 48 часов, автоматический цикл завершается с причиной
RETRY_WINDOW_EXCEEDED, а не отправляет раньше разрешённого времени. Ошибки конкретной
платформы нормализует адаптер по HTTP и структурированному ответу; произвольный текст description
не сохраняется без очистки и не становится единственным машинным правилом.

Для Telegram предусмотрен sendMessage; успешный ответ возвращает Message, параметры ошибки
могут содержать retry_after. Это сверено по [официальному Telegram Bot API](https://core.telegram.org/bots/api#sendmessage)
и [ResponseParameters](https://core.telegram.org/bots/api#responseparameters).
SDK, обработка конкретных кодов, доступность чата и полный сетевой сценарий ещё не проверены.
HTTP-клиент обязан скрывать токен в URL из диагностических логов и исключений.

## 7. Восстановление и наблюдаемость

У владельца в карточке виден notification_summary из ARCH-005: pending/sending/retry/sent/
blocked/failed/suppressed, число попыток, next_attempt_at, delivered_at, safe_error_code.
Это представление технического состояния, не дополнительный статус продажи.
Отдельного публичного endpoint доставки нет. Панель массового управления уведомлениями
в MVP не требуется. Узкий контракт команд доставки принят в ARCH-008.

Ручной перезапуск BLOCKED/FAILED — контролируемая операторская операция при реализации:
сначала устранить причину и проверить адресата, затем атомарно снять аренду, записать
причину/автора и вернуть тот же job в PENDING. Не создавать новую заявку/исходное событие.
Для SENT повторная отправка требует отдельного явного запроса, автоматически не поддерживается.
Историю прежнего цикла не стирать. Таблицы attempts, recipient_state, control_events,
версии и счётчики циклов согласованы в [схеме БД, раздел 8](database.md#8-уведомления-и-сессии).
Это единый источник физического контракта, а не дополнение на усмотрение исполнителя.

Операторский API согласован в [разделе 13 API](api.md#13-операторские-команды-доставки):
GET карточки job и POST команды RETRY/REASSIGN/SUPPRESS с авторизацией владельца,
CSRF, expected_version и Idempotency-Key. После переназначения BLOCKED/FAILED нужен
отдельный явный RETRY. SENDING нельзя изменять до завершения/восстановления аренды;
SENT/SUPPRESSED не возобновляются. Все изменения имеют аудит и сохраняют ограничения
частоты назначения. Новые общие административные права или платёжные действия не вводятся.

Диагностика: число due/blocked/failed jobs, возраст старейшего, активность доставщика,
число попыток/успехов/неопределённых исходов. Без имён, контактов и токенов в labels/logs.
Если due-job ждёт более 2 минут при работающей системе, показывается предупреждение о задержке;
это внутренний технический порог, не гарантия мгновенной доставки.
Проблема видна в CRM и серверной диагностике. Внешний мониторинг/другой канал оповещения
не настроен этой задачей; при неработающем сервере сама CRM не может предупредить владельца.

При очистке персональных данных сначала остановить/дождаться активных отправок и подавить
соответствующие jobs по ARCH-006; повторная аренда не должна воскресить их. Уже отправленное
сообщение не удаляется автоматически. После восстановления БД из резервной копии доставщик
стартует на паузе до сверки потерянного интервала и старых SENT/неопределённых исходов.
Срок диагностических attempt-записей — 30 дней после окончания цикла; затем сохраняются
итоги и аудит перезапуска без тел сообщений. Уникальность job не удаляется очисткой попыток.

## 8. Приёмка реализации

| Сценарий | Ожидаемый результат |
| --- | --- |
| Заявка из каждого из трёх каналов и ручной ввод | Один job соответствующего события с верным доверенным назначением |
| Повтор submit; rollback создания | Нет второго job; при rollback нет ни заявки, ни job |
| Платформа недоступна | Заявка и её успешная квитанция сохранены, повтор только доставки |
| Два доставщика захватывают один job | Одна действующая аренда, устаревший результат отклонён |
| Процесс упал до вызова / после вызова | Восстановление аренды, ограниченный повтор, честная неопределённость |
| Ответ rate limit | Retry-After соблюдён, ранней отправки нет |
| Адресат заблокировал бота / ошибка credentials | BLOCKED, никакой рассылки другим чатам |
| Исчерпаны попытки / прошло 48 часов | FAILED виден в CRM; без бесконечного цикла |
| Оператор исправил адресата и перезапустил | Тот же job, новый цикл, история сохранена |
| Изменена/закрыта заявка до отправки | Исторический текст поступления, актуальная карточка по ссылке |
| Вредоносный комментарий/Host/подставленный chat_id | Не меняет сообщение, ссылку или адресата |
| Очистка / восстановление backup | Нет автоматического возобновления подавленных/старых отправок |
| Успех платформы | SENT не меняет оплату, подтверждение, факт прочтения |

Эти проверки запланированы; реальные Telegram/VK credentials не использованы, сообщения не отправлены.
До пилота: проверенный адресат и бот, HTTPS CRM, явный тест доставки по разрешению владельца,
проверка фонового процесса и отображения ошибок. Схема и операторские команды согласованы
в ARCH-008. Далее — облачная реализация по процессу v2 с проверкой реальных транзакций
и отказов; принятый документ не заменяет интеграционные тесты.
