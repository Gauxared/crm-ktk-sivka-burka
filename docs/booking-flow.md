# Жизненный цикл заявки и общей прогулки

Status: ACCEPTED
Задача: ARCH-004. Версия: 1.0. Дата: 2026-09-13.
Основание: [требования](requirements.md), [контекст](architecture.md), [домен](domain-model.md).
Документ описывает поведение, не реализацию API или базы.

## 1. Независимые состояния

У заявки есть статус обработки, у прогулки — состояние общего плана, у участия —
состояние связи заявки с прогулкой. Деньги и доставка уведомления учитываются отдельно.
Клиент отправляет намерение; только владелец подтверждает условия, время и фактические оплаты.
Возраст/вес/опыт не являются автоматическими переходами в отказ.

Принятый минимальный набор статусов заявки:

| Код | Название | Смысл |
| --- | --- | --- |
| NEW | Новая | Заявка принята; владелец ещё не начал согласование |
| NEGOTIATING | Согласование | Идёт общение, уточнение времени/условий или ожидание договорённостей |
| CONFIRMED | Подтверждена | Владелец подтвердил участие и согласованный план |
| COMPLETED | Услуга оказана | Владелец отметил фактическое оказание услуги этой заявке |
| CANCELLED | Отменена / отказ | Обращение закрыто без оказания услуги; причина сохранена |

«Ожидаем предоплату», «не хватает остатка», «уведомление не доставлено» — признаки
карточки, не ещё три конкурирующих статуса заявки. NEW/NEGOTIATING без прогулки видны
в списке; при согласованном предварительном плане возможна связь с календарём с явной
пометкой «согласование», которая не выдаётся за подтверждение участия.

## 2. Команды владельца и переходы заявки

| Действие | Исходное состояние | Результат | Существенные условия/эффекты |
| --- | --- | --- | --- |
| Принять отправку | Заявки ещё нет | NEW | Обязательные поля и ключ отправки проверены; повтор возвращает существующий результат |
| Начать согласование | NEW | NEGOTIATING | История действия; чтение карточки само не меняет статус |
| Подтвердить | NEW / NEGOTIATING | CONFIRMED | Владелец явно принимает участие, есть согласованное время и актуальное участие в PLANNED-прогулке; предоплата не обязательна |
| Вернуть на согласование | CONFIRMED | NEGOTIATING | Явное действие с причиной; деньги не удаляются; владелец выбирает, сохранить ли предварительную связь с прогулкой |
| Отметить оказание | CONFIRMED | COMPLETED | Владелец подтверждает факт оказания; полная оплата и её отметка не обязательны |
| Отменить / зафиксировать отказ | NEW / NEGOTIATING / CONFIRMED | CANCELLED | Причина, отсоединение актуального участия; остальные заявки не отменяются; финансовое решение отдельно |
| Возобновить обращение | CANCELLED | NEGOTIATING | Явное решение владельца с причиной, прежние деньги/история сохраняются, старая прогулка не восстанавливается автоматически |
| Исправить ошибочное завершение | COMPLETED | CONFIRMED или NEGOTIATING | Только исправление ошибочно отмеченного факта с причиной; целевое состояние выбирается по актуальному плану, не произвольно |

Подтверждение не требует нового ID заказа. Новая услуга того же клиента оформляется новой
заявкой; возобновление предназначено для продолжения прежнего обращения.
Отмена после реально оказанной услуги не используется как способ оформить возврат:
факт COMPLETED сохраняется, денежная договорённость учитывается отдельно.
Операции исправления не должны маскировать новое посещение или удалять действительные оплаты.

Изменение контакта/заметки не меняет статус. Изменение существенных условий владельцем
сохраняет историю; если условия снова требуют общения с клиентом, владелец явно возвращает
согласование. Публичный клиент не может сам изменить CONFIRMED, цену или финансовый учёт.
Модель не предполагает автоматического завершения по часам или отмены по истечении таймера.
Для подтверждения владелец проверяет выбранную услугу/участников и возможность оказания.
Если цена или длительность ещё уточняются, это явно видно в карточке; отсутствующие
значения не подменяются нулём или стандартной длительностью. Согласованное начало
нужно для календарного плана, но известная цена и наличие денег не являются gate перехода.

## 3. Общая прогулка и участие

Visit: PLANNED (запланирована), COMPLETED (проведена), CANCELLED (отменена).
Эти состояния не заменяют статусы отдельных заявок. VisitParticipation сохраняет:
актуальную связь либо завершённую историческую связь с причиной выхода — отмена,
перенос, снятие с плана или оказание услуги. Точная форма хранения относится к ARCH-006.
У заявки не более одной актуальной связи; история прежних связей не удаляется.

### Присоединение к общей прогулке

Владелец выбирает PLANNED-прогулку, видит время/услугу, связанные заявки и число людей,
проверяет совместимость формата/длительности и явно присоединяет заявку.
Совпадение времени не объединяет заявки автоматически. Число участников не используется
как лимит вместимости без отдельного правила владельца. Цены/деньги разных заявок не сливаются.
Присоединение может быть предварительным в NEGOTIATING; подтверждение — отдельное решение.
К закрытой прогулке нельзя добавить новое актуальное участие без её явного исправления/возобновления.

### Перенос отдельной заявки

Из NEW/NEGOTIATING можно уточнить пожелание без изменения группового плана.
Для запланированной заявки владелец выбирает новую либо создаёт отдельную PLANNED-прогулку.
Одной согласованной операцией закрывается прежняя актуальная связь и создаётся новая.
Статус подтверждения сохраняется, только если владелец подтверждает новое время;
иначе заявка возвращается в NEGOTIATING с предварительным планом или без него.
Если новая дата неизвестна — снимается актуальная связь, заявка переходит в NEGOTIATING,
остаётся в списке и сохраняет старый план в истории. Остальная группа не переносится.
Ручные отметки денег остаются у той же заявки. Владелец договаривается о предоплате
при переносе вне системы и при необходимости корректирует справочные данные/заметку.

### Перенос всей прогулки

Владелец видит все затронутые актуальные заявки до подтверждения изменения.
Общий план меняется согласованно, исходное время сохраняется в истории каждой затронутой
заявки/посещения. Владелец указывает, для каких заявок новое время согласовано;
для остальных сохраняется явно предварительный план и NEGOTIATING либо отдельный перенос.
Нельзя изменить время общей прогулки и оставить невидимые «старые» времена в карточках.
Автоматическая рассылка клиентам не добавляется: согласование выполняет владелец,
пока отдельное требование на такие уведомления не принято.

### Отмена одной заявки и пустая прогулка

Отмена одной заявки закрывает только её актуальное участие. Остальные заявки сохраняют
время, статус и деньги. Пустая PLANNED-прогулка не исчезает молча: видна владельцу
с признаком «нет участников», может быть использована повторно или явно отменена.
Автоматического удаления или завершения пустой прогулки нет.

### Отмена всей прогулки

Полная отмена Visit допустима, если ни для одной его заявки не зафиксировано фактическое
оказание услуги. Если часть клиентов уже обслужена, сохраняются их исходы, оставшимся
задаются отдельные исходы, а прогулка закрывается как проведённая с частичным участием.
Перед действием перечисляются актуальные заявки. Для каждой владелец выбирает:
окончательную отмену, перенос в другую прогулку либо NEGOTIATING без даты.
Только после определения исхода всех актуальных связей Visit становится CANCELLED.
Заявки и история не удаляются; деньги не изменяются из-за статуса прогулки.
Пакет не может частично отменить группу незаметно: при конфликте версий операция
не принимается целиком, владелец получает актуальный список для повторного решения.

### Завершение прогулки

Прошедшее время само не завершает Visit. Владелец проверяет исход каждой актуальной
заявки: услуга оказана, отказ/неявка, перенос/продолжение согласования.
«Неявка» — причина, указанная владельцем, а не событие таймера или новый платёжный штраф.
Visit становится COMPLETED, когда фактические исходы всех участий отражены и не осталось
неразрешённых актуальных связей. Ранее закрытые исходы заявок не перезаписываются.
Если услуга не оказана никому, вместо ложного COMPLETED используется отмена прогулки.
Массовое действие предлагает исходы, но не делает всех клиентов автоматически оплатившими.
Если фактическое оказание отмечают для NEW/NEGOTIATING-заявки, владелец сначала подтверждает
её план; интерфейс может объединить подтверждение и завершение в одно явное действие,
но сервер сохраняет обе смысловые операции и проверяет их условия. Пропущенное
нажатие промежуточного статуса не требует фиктивной оплаты.

| Переход Visit | Условие |
| --- | --- |
| Создание → PLANNED | Владелец задаёт план; пустой план явно обозначен |
| PLANNED → COMPLETED | Есть фактическое оказание хотя бы одной заявке, исходы остальных отражены, актуальных неразрешённых связей нет |
| PLANNED → CANCELLED | Оказанных услуг в этом посещении нет; все актуальные связи разрешены |
| COMPLETED / CANCELLED → PLANNED | Только явное исправление/возобновление с причиной и проверкой связей, по разделу 5 |

Факт оказания проверяется и по историческим участиям этой прогулки, а не только
по оставшимся актуальным связям. Закрытый результат не меняется простым удалением участника.

## 4. Ручные отметки об оплатах — без платёжного модуля

Пользователь подтвердил три решения:

- Владелец может подтвердить запись без предоплаты.
- Платёжного модуля не будет: оплату, перенос денег и возвраты владелец решает вручную.
- Оказание услуги и расчёт независимы; COMPLETED допустим при неотмеченном остатке.

В CRM остаются справочные данные из ARCH-001: согласованная стоимость, обычная ожидаемая
предоплата 50% с возможностью индивидуальной договорённости, вручную отмеченные поступления
и отображаемый остаток, когда его можно вычислить. Это часть карточки заявки, не отдельный
платёжный продукт, бухгалтерия или интеграция с банком.

Ручная отметка не отправляет денег, не проверяет перевод, не создаёт ссылку на оплату,
чек, автоматическое удержание, обязательство возврата или автоматический зачёт другой заявки.
Сайт и боты не подтверждают факт оплаты по кнопке клиента, сообщению или скриншоту.
Не вводятся состояния «ожидает банковского подтверждения» и платёжные webhooks.

Отмена и перенос меняют план/статус, но не переписывают суммы. Договорённости о возврате
или переносе предоплаты владелец фиксирует заметкой и при необходимости обновляет ручные
отметки. Фактически состоявшийся возврат должен быть различим с ошибкой первоначального
ввода, если его сумма отражается в справочном расчёте: оригинальные данные и причина сохраняются.
Специальный workflow согласования возврата, автоматический процент удержания и расчёт
штрафов в MVP не требуются. Конкретный компактный формат ручных записей уточняется в ARCH-005/006.

Остаток по цене услуги — справочная арифметика, а не автоматически предъявляемый долг.
После отмены система показывает прежние суммы и комментарий владельца; не требует оплатить
всю отменённую услугу и не выставляет рассчитанный возврат. Неизвестная цена означает
неизвестный остаток; ввод ожидаемой предоплаты не увеличивает полученную сумму.

Исправление ошибочной ручной отметки не возвращает деньги. Корректировки после COMPLETED
или CANCELLED доступны владельцу с историей и не меняют факт оказания/отмены услуги.
Ни отсутствие предоплаты, ни недоплата, ни переплата не блокируют подтверждение, перенос,
отмену или фиксацию факта оказания. Ответственность за реальные расчёты остаётся у владельца.

## 5. Исправления закрытых состояний

Историческая ошибка исправляется отдельной командой владельца с причиной и проверкой
затронутых заявок/прогулки. Это не свободное редактирование строки status.
Если ошибочно закрытое посещение требуется вновь сделать PLANNED, владелец сначала
проверяет его дату и исходы заявок; уже подтверждённые отдельные исходы не откатываются молча.
Восстановление участия не создаёт вторую актуальную связь и не переносит другие заявки
из новых прогулок обратно автоматически. Система должна показать конфликт вместо потери данных.
COMPLETED → CONFIRMED допустим только с валидным актуальным планом; иначе используется
NEGOTIATING и отдельное повторное согласование. Факты денежных операций сохраняются.

## 6. Согласованность, повторы и права

- Все служебные переходы доступны только авторизованному владельцу, проверяются backend.
- Создание/перенос участия, изменение статуса и история образуют согласованное изменение.
- Для общегрупповых операций проверяются версии Visit и всех затронутых заявок/связей.
- Устаревшая вкладка не перезаписывает свежий результат; конфликт возвращается без частичного успеха.
- Ключ повтора относится к конкретному действию, а не человеку. Повтор принятого действия
  возвращает прежний результат; тот же ключ с другим содержимым не выполняет новую команду.
- Повтор команды отметить деньги не создаёт второе поступление. Новая реальная оплата —
  отдельная явная команда с другим идентификатором действия.
- Ошибка отправки уведомления не откатывает сохранённую заявку. Транспортное подтверждение
  мессенджера не считается подтверждением записи, прочтением или оплатой.
- Пересечение времени разных прогулок не является автоматическим запретом: ресурсной
  модели лошадей/тренеров в MVP нет, загрузку согласует владелец.

| LC-13 | Повтор ручной отметки одной оплаты | Нет второго поступления из-за сетевого повтора |
| LC-14 | Владелец подтверждает согласованную запись при нулевых поступлениях | CONFIRMED, без требования отметить предоплату |
| LC-15 | Владелец отмечает оказание при неотмеченном остатке | COMPLETED; справочный остаток сохранён отдельно |
| LC-16 | Отмена после предоплаты | CANCELLED; прежние суммы сохранены, нет автоматического возврата или штрафа |
| LC-17 | Перенос с ранее отмеченной предоплатой | Новый план, те же денежные записи, нет фиктивной повторной оплаты |
| LC-18 | Исправление ручной суммы у завершённой заявки | История исправления сохранена; COMPLETED не откатывается |
| LC-19 | Подтверждение при цене по договорённости | Цена явно неизвестна до решения владельца, не 0; согласованный календарный план возможен |

Эти примеры являются критериями будущих тестов, не отчётом об уже реализованном приложении.

## 8. Передача и статус решений

ARCH-005 определяет контракты команд, версии, обязательные поля и сообщения ошибок.
